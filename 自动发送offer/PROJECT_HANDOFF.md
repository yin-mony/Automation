## 1. 项目目标与最终业务场景

这是一个企业微信自建应用，供公司人事在企业微信工作台内使用：

1. 人事上传候选人简历图片、PDF 或 DOCX。
2. 程序提取候选人的公开基本信息。
3. 人事在单页表单中复核录用岗位、部门、薪酬、入职和报到信息。
4. 二次确认后生成正式 Offer PDF。
5. 生成本地 `.eml`，同步腾讯企业邮箱草稿箱，并真实发送到候选人邮箱。
6. 真实邮件必须带上 `Cc` 抄送字段，把负责人/上级加入同一封 Offer 邮件，确保候选人点击“回复全部”时抄送人能收到回复。

候选人不需要加入企业微信。本应用仅供企业内部人事操作。

## 2. 当前技术结构

- 后端：Flask + Gunicorn
- 页面：Jinja2 服务端渲染
- UI：本地 Tabler UI 1.4.0 + 自定义 CSS + 原生 JavaScript
- OCR：RapidOCR ONNX Runtime
- PDF：ReportLab
- 邮件：SMTP 真实发送 + IMAP 草稿箱留存
- 数据：本地 JSON 任务目录，无数据库

核心文件：

| 文件 | 职责 |
| --- | --- |
| `run.py` | Flask 路由、企业微信网页授权、表单提交、发送编排 |
| `resume.py` | 图片/PDF/DOCX 读取、OCR 和简历字段提取 |
| `offer.py` | 正式 Offer PDF 生成 |
| `draft.py` | 邮件正文、EML、SMTP、IMAP 草稿箱 |
| `jobs.py` | 本地任务状态和 JSON 持久化 |
| `settings.py` | 配置归一化、目录和中文字体选择 |
| `templates/index.html` | 上传、复核、结果三个状态的单页模板 |
| `static/style.css` | 企业微信桌面端和移动端样式 |
| `config.py` | 本地真实配置，包含敏感信息，禁止覆盖生产配置或对外分享 |
| `config.example.py` | 无敏感信息的配置示例 |
| `tests/test_workflow.py` | 核心 OCR、PDF、邮件流程测试 |

## 3. 当前已实现功能

- 企业微信静默网页授权，仅允许企业成员进入。
- 简历上传及公开信息识别。
- 部门下拉选择，直属上级可自动匹配部门。
- 日期使用日期控件，报到时间使用时间控件。
- 试用期和转正薪酬均按“基本工资 + 保密费 + 绩效 = 总薪酬”自动计算。
- 工资卡固定为“中国建设银行”，页面不允许手工修改。
- 试岗说明独占一行，工资卡信息在下一行单独展示。
- 试岗结算规则：
  - 公司评估未达到岗位要求并终止试岗：100 元/日；
  - 员工试岗期间主动退出：50 元/日。
- PDF 正文使用首行缩进、两端对齐，并保护日期、金额等短语不被错误拆行。
- 生成 PDF、EML、企业邮箱草稿并真实发送邮件。
- 支持在 Offer 邮件中写入固定 `Cc` 抄送人；复核页、确认弹窗和结果页只显示姓名，不展示邮箱。
- 发送按钮有二次确认和 CSRF 防护。
- `FLASK_SECRET_KEY` 必须固定；缺失时程序明确报错，避免 Gunicorn 多进程会话失效。
- OCR 和发送阶段显示处理中遮罩，防止重复提交。
- 静态资源带版本参数 `20260824-ui2`。
- 当前自动化测试：`python -m pytest -q`，最近结果为 `4 passed`。

## 4. 当前页面设计决定

用户明确选择“方案 A”：

- 必须是单页连续表单；
- 不要右侧审核摘要；
- 不要分页向导；
- 不要左侧章节栏；
- 不要重复展示同一信息；
- 使用横向章节标题分隔候选人信息、录用条件、报到与发件；
- 薪酬计算式保持横向清晰展示；
- 试岗说明与工资卡必须分成上下两行。

当前 `index.html` 和 `style.css` 已按上述方向调整，并做过本地桌面端完整截图检查。

## 6. 部署注意事项

不要直接上传或覆盖生产服务器的 `config.py`，其中包含：

- 企业微信 CorpID、AgentID、Secret；
- Flask 会话密钥；
- 腾讯企业邮箱 SMTP/IMAP 凭证；
- 组织架构和默认人事信息；
- 中文字体路径。

代码更新通常只覆盖对应源码和静态文件，然后在宝塔重启 `offer_app`。

当前根目录中的 `offer_app_minimal_deploy.zip` 是早期生成包，晚于该压缩包的代码修改较多。下一次正式发布前必须以当前源码重新生成部署包并做文件哈希核对，不能直接复用旧压缩包。

运行时目录由程序创建，不应放入部署包：

- `data/`
- `output/`
- `logs/`
- `__pycache__/`
- `.pytest_cache/`
- `tests/`

## 7. 当前最重要的业务修正

### 抄送是邮件 Cc，不是企业微信审批

2026-08-24 用户明确纠正：当前最关键的是 Offer 邮件里的“抄送”操作，而不是企业微信审批。

正确方向：

- 候选人邮箱写入 `To`；
- 负责人/上级邮箱写入 `Cc`，但页面和企业微信内部通知只展示姓名；
- 本地 `.eml`、企业邮箱草稿箱和 SMTP 真实发送必须保持同一份邮件头；
- 二次确认弹窗需要展示收件人和抄送人；
- 结果页需要展示邮件抄送状态；
- 候选人按邮件正文要求“全部回复”时，抄送人应进入同一邮件线程。

当前代码已经新增固定抄送人配置项：

```python
OFFER_CC_RECIPIENTS = [
    {"name": "何倩怡", "email": "heqianyi@bonison.net"},
    {"name": "宁致远", "email": "ningzhiyuan@bonison.net"},
]
```

兼容旧配置 `OFFER_CC_EMAILS`；如果旧配置中包含 `heqianyi@bonison.net` 和 `ningzhiyuan@bonison.net`，页面会自动映射显示为“何倩怡、宁致远”。

不要把这个需求实现成企业微信审批 `applyevent`，也不要再等待审批模板 ID 或控件 ID。

## 8. 企业微信相关排障记录

- 错误 `60020 not allow to access from your ip`：服务器公网 IP 未加入自建应用企业可信 IP。
- 已知服务器出口 IP：`47.251.101.28`。
- 普通应用消息接口即使 `errcode=0`，也可能返回 `invaliduser`；当前代码已补充检查 `invaliduser`、`invalidparty`、`invalidtag`。
- UserID 必须使用企业微信通讯录中的“账号/UserID”，不能使用姓名、手机号、邮箱或 AgentID。
- 企业微信应用通知接收人必须处于自建应用可见范围内；这和邮件 `Cc` 抄送不是同一个概念。

## 9. 下一轮建议执行顺序

1. 阅读本文件和 `README.md`。
2. 运行 `python -m pytest -q`，确认当前基线仍为 4 个测试通过。
3. 确认生产 `config.py` 中 `OFFER_CC_RECIPIENTS` 或旧版 `OFFER_CC_EMAILS` 是否配置为真实负责人/上级邮箱。
4. 使用测试邮箱完成一次端到端验证，检查收件人、Cc、本地 EML、企业邮箱草稿箱和真实发件是否一致。
5. 如需要自动匹配直属上级邮箱，补充配置映射和测试。
6. 重新制作最小部署包，排除运行时目录与敏感配置，并校验哈希。

## 10. 安全与业务约束

- 不得在日志、交接文档、截图或部署包中泄露 Secret、邮箱授权码和 Flask 会话密钥。
- 真实发送必须保留二次确认。
- 企业微信通知失败，不能自动重发已成功发送的候选人邮件。
- 后续如增加“重试抄送”，必须明确是重新发送邮件还是只补发内部通知；默认不得再次执行 SMTP 发送，避免候选人重复收到 Offer。
- 试岗结算文案涉及劳动用工规则，正式长期使用前建议由人事或法律顾问复核。
