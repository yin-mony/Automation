# Automation 通用代码结构与推送规范

> 本文档为 `Automation/` 仓库全局强制规范。所有一级业务子项目的新建、重构、维护和推送都必须遵守。
> 子项目可以补充更具体的规范，但不得覆盖或放宽本文档要求。

## 1. 适用范围

- 适用于仓库根目录下每个一级业务子项目。
- 子项目已有 `docs/NAMING.md` 时，以本文档为全局底线，再叠加子项目本地规范。
- 本文档优先约束代码结构、命名、注释、配置存放、打包入口和远程推送行为。

## 2. 代码结构规范

- 每个 `.py` 文件原则上只保留一个顶层主类，文件名与主类职责对应。
- GUI 子项目统一使用 `run.py` 作为窗口入口，窗口页、日志流等仅服务 GUI 的类可以作为 `RunGui` 内部子类。
- 业务主流程应保留在职责明确的主逻辑文件中，不随意拆到泛化文件。
- 禁止随意新增 `utils.py`、`helper.py`、`common.py`、`manager.py`、`handler.py` 等泛化文件名。
- 打包脚本必须直接以真实入口文件打包，例如 GUI 项目直接打包 `run.py`。
- 重构旧流程时，用户要求保留的旧代码和注释必须按归档注释保留，便于后续对照。

## 3. 命名规范

- 类名使用 `PascalCase`。
- 方法名、变量名使用 `camelCase`。
- 禁止新建 `_` 开头的方法或函数，`__init__` 等 Python 内置特殊方法除外。
- 文件名保持简短、准确，优先使用能直接表达职责的单词。
- 方法名应简短直观，避免堆砌多个业务词。

## 4. 配置与默认值

- 类内默认值、固定 URL、状态变量等优先写在 `__init__` 中。
- 单文件调试配置统一写在 `if __name__ == "__main__"` 的 `config` 字典中。
- GUI 运行缓存、本地账号密码、API Key、Webhook、路径等本地配置文件必须加入 `.gitignore` 或明确不参与远程提交。
- 需要发布示例配置时，使用 `.example`、模板文件或 README 说明，不用真实本地配置充当模板。

## 5. 本地配置与远程推送

- 执行远程仓库提交、推送、同步前，不允许为了脱敏远程内容而直接清空、脱敏、覆盖本地真实配置文件。
- 本地配置必须保持真实可用；远程仓库需要安全版本时，只能通过临时副本、示例配置、`.gitignore`、路径限定暂存或推送后恢复校验等方式处理。
- 如果某个配置文件包含账号、密码、API Key、Webhook、Cookie、Token、本机路径等敏感或本地专属信息，应优先排除出 Git 暂存范围。
- 若确实需要向远程提交配置结构，只提交不含真实密钥的模板文件，并保留本地真实配置文件不变。
- 推送前后必须检查 `git status` 和目标配置文件状态，确认没有把本地配置误清空、误脱敏或误提交。

## 6. 注释与文档

- 类和方法使用中文 docstring 描述职责。
- 关键流程步骤使用中文注释说明。
- 子项目行为、入口、依赖、打包方式、输出路径变更时，同步更新子项目 README。
- 新增或重命名一级子项目时，同步更新仓库根目录 README 的子项目索引。

## 7. 提交前自检

- [ ] 文件名简短且能表达职责。
- [ ] 文件内没有无意义拆分或泛化工具文件。
- [ ] GUI 入口是 `run.py`，业务流程入口清晰。
- [ ] 类名、方法名、变量名符合命名规范。
- [ ] 关键流程有中文 docstring 和必要注释。
- [ ] 本地配置文件没有被清空、脱敏或覆盖。
- [ ] 含敏感信息的配置未进入暂存区。
- [ ] README 与实际入口、依赖、打包方式一致。
